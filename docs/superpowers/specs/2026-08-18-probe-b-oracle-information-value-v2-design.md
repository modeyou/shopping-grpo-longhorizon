# Probe B V2：低成本 Oracle 信息价值筛查设计

- 日期：2026-08-18
- 分支：`dev/innovation`
- 状态：已获用户批准，待实现计划
- 预算：计划 25 个任务对，最多 50 次真实轨迹尝试；无效尝试也占预算

## 1. 决策摘要

Probe B V2 先回答一个比“Agent 会不会自主提问”更基础的问题：

> 当购物指令缺少一个当前购买约束时，在购物前向 Agent 提供该约束，能否提高严格成功率与隐藏字段满足率，同时不增加真实错误购买？

V2 采用低成本、受控的两臂配对筛查：

1. **Under / No-Ask**：只提供欠约束查询；
2. **Under / Oracle-Ask**：提供同一欠约束查询，并在第一次模型生成购物动作前插入预先登记的 Oracle 问答。

每条任务只隐藏一个字段，每臂只尝试运行一次。首轮最多尝试 50 条真实轨迹，不为无效轨迹自动补跑。V2 不测试自主提问、不引入用户画像、不开展 SFT/GRPO，也不形成正式统计显著性结论。

本设计替代 `2026-08-18-probe-b-multiturn-personalization-design.md` 中第一轮探针的执行臂、数据语义和判据；旧文档作为历史设计保留。

## 2. 范围与诚实边界

### 2.1 V2 要验证的内容

- 单个未披露的当前购买约束是否具有可测的信息价值；
- Agent 得到该信息后，是否把它落实到最终商品选择；
- 固定 Oracle 信息是否能减少因欠约束导致的失败，而不制造更多错误购买。

### 2.2 V2 不验证的内容

- Agent 能否判断何时需要提问；
- Agent 能否提出相关、自然且高价值的问题；
- 多个隐藏字段下的多轮对话能力；
- 真实长期用户画像带来的个性化收益；
- 澄清数据用于 SFT/GRPO 后的训练收益；
- 论文级统计显著性或泛化结论。

因此，V2 通过时只能表述为“固定披露一个缺失约束在该筛查集上显示出正向机制信号”，不能表述为“自主澄清有效”或“个性化有效”。

## 3. 信息语义

V2 明确区分三类信息：

- `explicit_query`：用户已经说出的本次购买需求；在数据中由 `under_query` 表达；
- `latent_goal`：本次购买真实存在、但用户尚未说出的一个约束；Oracle 问答只披露它；
- `user_profile`：跨任务相对稳定的长期偏好、人口属性或历史行为；V2 不提供、不模拟也不评分。

未来若引入画像，信息优先级必须是：本次明确需求或澄清回答高于长期画像。画像只能作为搜索、排序和减少重复提问的先验，不能覆盖当前用户回答，也不能充当当前任务答案表。

## 4. 任务集设计

### 4.1 来源与规模

- 沿用当前 25 条 Probe B 任务的训练来源；
- 所有任务必须来自 SFT 训练数据，不得与 `data/evaluation/tasks.jsonl` 重叠；
- 保留原始 `task_id`，环境仍按原始完整任务恢复 `TaskFacts` 并用 Reward v3 评分；
- 不因模型表现替换任务或事后修改隐藏字段。

### 4.2 单字段隐藏

每条任务只隐藏一个字段。目标分层为：

| 隐藏字段 | 任务数 | Reward 角色 |
|---|---:|---|
| 预算 | 13 | 硬门控 |
| 颜色 | 6 | 软偏好或选项约束，按原任务事实标注 |
| 品牌 | 3 | 软偏好 |
| 产地 | 3 | 软偏好或功能属性，按原任务事实标注 |
| 合计 | 25 | — |

现有任务清单已经具备 18 条颜色候选、4 条真实品牌候选和 3 条产地候选，因此必须满足上述精确分层。具体任务到隐藏字段的映射在 API 运行前写入任务清单并冻结；不得为了运行结果调整。

### 4.3 查询自然性

- `clear_query` 保留原始完整需求；
- `under_query` 只删除或自然改写目标字段，不得泄漏其值或同义表达；
- 不使用“颜色您帮我选，但其实只接受黑色”这类与后续精确回答矛盾的句子；
- 删除字段后，查询仍应是自然、可购物但信息不完整的中文请求；
- Oracle 答案必须给出 Reward 可判定的准确值，不使用“别太贵”“差不多”等模糊表述。

### 4.4 数据结构

每条任务采用以下结构：

```json
{
  "task_id": 16576,
  "clear_query": "我想买一台黑色咖啡机，预算不超过1000元。",
  "under_query": "我想买一台黑色咖啡机。",
  "latent_goal": {
    "field": "budget",
    "raw_value": "1000元以内",
    "normalized_value": {
      "operator": "<=",
      "amount": 1000,
      "currency": "CNY"
    },
    "reward_role": "hard_gate",
    "source_span": "预算不超过1000元"
  },
  "oracle_turn": {
    "question": "这次购买的预算上限是多少？",
    "answer": "预算不超过1000元。",
    "answer_facts": {
      "budget_max": 1000,
      "currency": "CNY"
    }
  },
  "provenance": {
    "source_split": "sft_train",
    "source_task_id": 16576,
    "construction_version": "probe_b_v2",
    "review_status": "approved"
  }
}
```

颜色、品牌和产地使用同一外层结构，并在 `normalized_value` 中保存对应的规范化属性值。

### 4.5 运行前静态不变量

数据校验器必须在零 API 成本下确认：

1. 每条任务恰好有一个 `latent_goal`；
2. `source_span` 和目标值存在于 `clear_query`；
3. `under_query` 不含目标值及人工登记的等价泄漏表达；
4. Oracle 问题只针对该字段，答案只披露该字段；
5. Oracle 答案的规范化事实与原始 `TaskFacts` 一致；
6. 25 个 `task_id` 唯一，来源合法且无评测集重叠；
7. 实际字段分布和任务文件哈希在真实运行前写入 manifest。

任何一项失败都阻止真实 API 运行。

## 5. 实验臂与公平控制

### 5.1 Under / No-Ask

- 初始用户消息为 `under_query`；
- 不暴露 `ask_user` 工具；
- Agent 直接使用购物工具完成任务或停止。

### 5.2 Under / Oracle-Ask

- 初始用户消息同样为 `under_query`；
- Runner 在第一次模型生成购物动作前，按任务文件插入一条固定 assistant 问题和一条固定 user 回答；
- 问题与回答不是模型生成的，不计入购物环境动作步数；
- 同样不暴露 `ask_user` 工具，防止把自主提问能力混入处理效应。

两臂唯一允许的差别是 Oracle 臂多出的预登记问答。两臂必须共用：

- 同一个系统提示词及其哈希；
- 同一个模型、接口、温度和工具 schema；
- 同一个环境版本、Reward v3 和 observation v2；
- 同一个 35 步购物环境上限；
- 同一套 Action Guard、动作规范化和终止规则。

`clear_query` 继续保存在任务文件中用于审计，但为了节省成本，V2 首轮不运行 Clear / Full-Info 臂。

## 6. 执行协议与成本保护

### 6.1 离线阶段

真实调用前必须依次完成：

1. 25 条任务的静态校验；
2. Oracle 对话注入的离线单元测试；
3. 两臂 Mock 端到端测试；
4. 指标计算的固定样例测试。

这些步骤不得调用付费模型 API。

### 6.2 真实筛查阶段

- 每条任务、每个实验臂只运行一次；
- 温度固定为 `0`；如果目标接口不支持绝对零温度，则使用其最低受支持值并记录；
- 使用固定种子 `20260818` 生成任务顺序和每个任务内的臂顺序；
- 首先只尝试运行一个任务对。无论是否有效，这两次尝试都占用首轮预算；若两条轨迹有效，它们直接计入最终 25 对；
- 人工检查该任务对的消息顺序、环境步数和 Reward 明细后，才运行剩余 24 对；
- 首轮真实轨迹尝试上限为 50 次，即每个任务—实验臂组合最多一次；无效轨迹不自动补位，因此有效结果可能少于 25 对；
- Runner 必须支持按任务对断点续跑，已完成的有效轨迹不重复调用；
- 真实运行需要单独获得用户明确许可。批准设计或实现不等于批准 API 执行。

Runner 还必须提供全局 `max_llm_calls` 硬上限。首轮默认值为 700；达到上限时安全保存并停止，不启动新调用。不得自动提高上限。

### 6.3 异常与失败分类

- API、网络或环境服务异常属于基础设施异常；对应轨迹标为 `invalid`，不进入指标；
- 基础设施异常不自动重跑整条轨迹。补齐缺失任务对需要用户另行批准，并视为超出首轮 50 次预算的新运行；
- 模型无工具调用、非法动作、重复循环、提前放弃或达到最大步数属于 Agent 行为结果，必须保留并按正式规则计分，不能标成基础设施异常；
- 环境 lease 必须在 `finally` 中释放；
- 一旦单个任务对只有一臂有效，该任务对不进入配对汇总，并在缺失清单中明确列出；
- 若未得到 25 个完整有效任务对，则只报告已完成结果，不能应用“通过/不通过”判据。

## 7. 记录与可复现性

每次运行写入新的 `run_id` 目录，禁止向旧结果文件追加。Manifest 至少记录：

- `run_id`、开始时间和代码 Git commit；
- 任务文件哈希、任务顺序、臂顺序和随机种子；
- 模型名、API base 标识、温度、最大环境步数和 `max_llm_calls`；
- 系统提示词哈希、工具 schema 版本、环境和 Reward 版本；
- 已完成、无效和缺失的任务对；
- 累计模型调用次数。

不得记录 API key。每条轨迹至少保存：

- 完整 message history；
- 每一步 observation、原始模型响应、规范化 action 和工具结果；
- Oracle 问答是否按预期注入；
- 最终购买商品与目标；
- `reward`、`reward_type`、`reward_valid`、reward detail；
- `termination_reason`、环境步数和基础设施异常信息。

## 8. 指标与预登记判据

### 8.1 主要指标

严格成功遵循仓库契约：终局为完整 `gold_purchase` 且 `reward_valid=true`。

主要效应为：

```text
Delta_strict = Oracle-Ask 严格成功率 - No-Ask 严格成功率
```

分析必须按 `task_id` 配对，报告：

- No-Ask 失败、Oracle 成功的任务数；
- No-Ask 成功、Oracle 失败的任务数；
- 两臂都成功和两臂都失败的任务数；
- 净增加的成功任务数及百分点评估。

### 8.2 机制与安全指标

- **隐藏字段满足率**：最终购买商品是否满足该任务的 `latent_goal`；
- **真实错误购买数**：只统计 `reward_type == "wrong_purchase"`；
- **步数与终止类型**：用于诊断信息是否减少搜索或改变停止行为，不作为通过门槛。

隐藏字段满足使用字段专用的确定性校验：预算比较成交价与上限；颜色、品牌和产地比较所选商品规范化属性与 `normalized_value`。若没有发生购买，该字段记为未满足，但同时保留终止类型，避免与错误购买混淆。

### 8.3 低成本继续门槛

只有 25 个任务对全部有效时，V2 才能判为“出现值得继续的机制信号”。三个条件必须同时满足：

1. Oracle 相对 No-Ask **净增加至少 3 个严格成功任务**，即至少 `+12` 个百分点；
2. Oracle 的隐藏字段满足率高于 No-Ask；
3. Oracle 的真实 `wrong_purchase` 数量不高于 No-Ask。

若三项没有同时满足，则不进入自主提问扩展，先报告失败模式。单次、25 任务的结果只作描述性筛查；可以附精确 McNemar 结果，但不能因为 p 值或趋势而改写预登记门槛，也不能宣称统计显著。

## 9. 测试与验收

实现进入真实运行前必须通过以下验收：

- 数据校验器覆盖七项静态不变量，并对泄漏、双隐藏字段和事实不一致样例失败；
- Mock 测试证明两臂提示词、工具和动作预算一致，差异只有固定 Oracle 问答；
- Oracle 问答不消耗 35 步购物环境配额；
- Action Guard 对无工具调用、非法参数和多工具调用使用同一正式规则；
- 指标测试能区分 `wrong_purchase`、提前停止、循环和最大步数；
- 配对分析拒绝只有单臂有效的任务对；
- 输出目录不会混合不同 `run_id`，断点续跑不会重复有效轨迹；
- 全局调用上限触发时可以安全保存并退出；
- 环境异常时 lease 仍被释放；
- 一对真实冒烟轨迹经人工检查合格后才允许继续剩余任务。

## 10. 后续决策

如果 V2 达到继续门槛，下一阶段再加入 **Autonomous-Ask** 臂，用 Oracle-Ask 作为信息价值上限，并衡量：相关问题率、隐藏字段恢复率、答案利用率和 Oracle 信息捕获效率。

只有自主澄清机制成立后，才进入真正的用户画像实验。正式画像实验应将 `latent_goal` 与 `user_profile` 分开，并采用“无画像/有画像 × 无对话/有对话”的 2×2 设计。

如果 V2 未达到门槛，则先根据完整轨迹区分：信息本身没有决策价值、Agent 未利用答案、任务隐藏方式不自然，或环境/Reward 无法反映目标字段。不得通过改任务、挑子集或追加有利样本来追求通过。
