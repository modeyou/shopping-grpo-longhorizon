# 个性化主动澄清购物 Agent：项目契约

- 日期：2026-08-19
- 正式开发分支：`feat/personalized-clarification-agent`
- 状态：方向已对齐；Reward、正式评测和训练超参数待分阶段确认
- 基础：`shopping-grpo-longhorizon` 开源训练与评测流水线

## 1. 项目目标

本项目不是把原仓库原样复现一遍，也不是只在其上增加一个独立探针。目标是以
ShopSimulator 为环境底座，完整实现一个具有明确差异化的 Agentic RL 项目：

> 面向信息不完整且存在长期偏好的购物请求，让 Agent 联合使用当前请求与用户画像，
> 判断是否需要主动澄清，并通过 SFT 与 GRPO 学会高效地选择满足本轮硬约束和个体偏好的商品。

项目最终必须打通：数据构造、SFT、在线 GRPO、工具交互、Reward、评测、消融和错误分析。
公开环境、商品目录、任务目标、内嵌画像与个性化请求的继承关系必须保留并如实说明；正式训练与专项评测
轨迹由本项目在扩展环境中自行采集。多轮交互协议、训练策略、Reward 扩展和专项评测构成本项目的主要个人实现。

## 2. 统一创新主线

个性化、用户画像、主动澄清和 Reward 改造不是四个互不相关的功能，而是一条决策链：

```text
当前请求 + 长期用户画像
        ↓
已知硬约束 / 可推翻的偏好先验 / 关键未知信息
        ↓
信息充分：搜索与购买  |  信息不足：ask_user
        ↓
澄清回答更新本轮状态
        ↓
满足硬约束并兼顾画像偏好的商品选择
```

V2 已证明披露隐藏约束能将严格成功率从 76% 提升至 96%；V3 中 zero-shot Agent
在 10/10 个任务上均未提问。这两项结果只作为立项证据：信息具有价值，但提问策略需要训练。

## 3. 相对原项目的改造边界

| 模块 | 原项目 | 本项目必须实现 |
|---|---|---|
| 状态 | 当前购物请求 | 当前请求、静态画像、会话澄清状态 |
| 动作 | 搜索、查看、购买/停止 | 原动作空间加受限 `ask_user` |
| 数据 | 通用购物轨迹 | 通用轨迹加画像条件与澄清轨迹 |
| 策略 | 直接完成购物 | 判断问不问、问什么、如何利用回答 |
| Reward | 确定性终局 Reward v3 | 保留终局语义，增加画像匹配与提问效率信号 |
| 评测 | Final-200 通用购物 | 通用回归、个性化、主动澄清三轨评测 |

不重写 ShopSimulator 商品目录、浏览器执行层和基础工具；这些属于环境基础设施，而不是本项目的
创新目标。环境协议只做支持画像和澄清闭环所必需的扩展。

## 4. 信息语义与优先级

统一采用以下优先级：

```text
本轮明确要求 > 本轮澄清回答 > 适用于本轮对象的高置信画像事实
> 长期画像偏好 > 模型默认假设
```

- 本轮明确要求与澄清回答可以形成硬约束或明确偏好；
- 画像中的品牌、预算、颜色和功能等长期倾向是可被本轮请求推翻的软先验，不能冒充本轮明确要求；
- 本人尺码等少量高置信稳定事实，只有本轮适用对象明确且无冲突时才能直接作为操作约束；
- 除适用的稳定事实外，画像只在硬约束已经满足的候选之间参与排序；
- 模型不得仅凭画像补全高风险或决定性未知字段；
- 当前请求与画像冲突时，以当前请求为准，并将这一能力纳入训练与评测。

首版直接使用 ShopSimulator 提供并去除 `__reasoning__` 的 `user_persona`。人口学字段可以作为上下文存在，
但不进入 Reward；只有能由商品与购买结果验证的品牌、预算、颜色、规格和功能偏好参与个性化评测。

## 5. 主动澄清的任务定义

只有同时满足以下条件时才应提问：

1. 某字段对候选可接受性或排序有实质影响；
2. 当前请求和画像都不能可靠确定该字段；
3. 环境搜索本身不能低成本消除该不确定性；
4. 提问的预期收益高于新增交互成本。

首版每个任务最多允许两次自然语言提问，每次应只询问一个主要事实，不预先向 Agent 提供 gold 字段。
以下行为视为错误：询问已知字段、询问无关字段、重复提问、在信息完整任务中机械提问，以及得到
回答后不使用该信息。轨迹保留完整问答，字段分类和提问价值在离线评测阶段分析。

## 6. 数据与可复现性契约

- ShopSimulator 的商品目录、目标事实、`user_persona`、`instruction_sample` 和 `instruction_simple`
  作为基准输入保留；这部分不是本项目生成的数据；
- 原作者发布的 SFT/GRPO 轨迹不进入本项目正式模型的梯度数据；
- 本项目自行实现 persona 环境透传、Shopper 多轮回答、`ask_user`、教师环境 rollout、轨迹验收、划分和
  审计脚本；正式 SFT 和专项评测轨迹均由该管线重新采集；
- 自建训练集、开发集和专项评测集必须按 `task_id` 隔离；
- `data/evaluation/tasks.jsonl`（Final-200 Clean）保持冻结且不得进入梯度数据；
- 生成物记录来源版本、seed、字段分布、任务列表和 SHA256；
- LLM API 可以作为正式数据生成与教师轨迹采集的主要方式；所有响应必须经过 JSON schema、环境
  终局、跨字段一致性、泄漏和任务隔离检查，并保留人工抽检与修订记录；
- 探针中的 FakeProfile 不直接冒充正式画像数据，只能作为构造逻辑和失败案例的参考。

首轮规模不在此契约中写死。实施时先用最小样本验证数据语义与工具闭环，再根据类别覆盖和失败
模式确定正式规模，避免为了数量制造低质量样本。

## 7. 训练闭环

项目至少形成以下可复现路径：

```text
基础模型
  → 一次混合 SFT（本项目自建的通用购物、画像与澄清轨迹）
  → clarification-aware GRPO（在线 ShopSimulator）
  → 三轨评测与消融
```

“多轮轨迹”指一条样本内部包含多次 Agent、用户和环境交互，不等于 A/B/C 多阶段课程学习。
首版不采用课程学习：不同任务类型混合为一份训练集，执行一次 LoRA SFT run；是否增加 curriculum
只依据单次训练的分桶学习曲线和失败模式决定。SFT 先回答模型能否学会画像优先级、`should_ask`
和回答利用；GRPO 再优化成功率与交互效率。不得用 Reward 掩盖 SFT 数据或工具协议错误。

## 8. Reward 设计边界（具体方案后置）

当前阶段不冻结 Reward 分项、形式或权重。正式设计前先跑通数据、交互协议与 SFT，并根据真实失败
模式决定需要哪些学习信号。后续设计至少必须遵守：

- 硬约束失败时，画像匹配和提问奖励不能抵消错误购买惩罚；
- 个性化信号只奖励可由证据验证、且不与本轮请求冲突的偏好匹配；
- 澄清信号必须关注关键未知信息及回答利用，不能只奖励调用工具；
- 必须控制机械提问、无关提问、重复提问和忽略回答；
- 所有训练 Reward 必须确定性、可单测，不使用在线 LLM judge；
- 具体 Reward 方案在 SFT 失败模式出现后单独对齐和预登记。

## 9. 评测设计边界（具体方案后置）

当前阶段不冻结评测集规模、评分公式和全部对照组。正式设计时原则上保留三类互不污染的能力：

1. **General**：冻结的 Final-200，检查通用购物能力是否退化；
2. **Personalization**：检查硬约束满足后，画像偏好是否改善候选选择；
3. **Clarification**：同时包含应问和不应问任务，检查何时问、问什么及回答利用。

具体指标和消融在数据语义、交互协议与 Reward 明确后再设计。任何提升都必须使用任务隔离且条件
一致的对照进行归因，不能将不同模型、任务或运行条件的差异混为一个结论。

## 10. 成本与实施决策

- 目标是完成项目级闭环，不追求论文级多模型、多随机种子和大规模统计结论；
- 优先本地模型、规则用户模拟器和小规模诊断，付费 API 不作为正式训练依赖；
- 每阶段先通过离线测试和极小真实运行，再批准耗时训练；
- 只有最终候选模型运行一次完整 General 评测，中间迭代使用隔离的小型开发集；
- 是否扩大数据、训练步数或多轮澄清，只依据阶段评测和剩余预算决定。

## 11. 分阶段确认点

本契约冻结方向，不冻结所有实现参数。后续只在四个检查点进行局部确认：

1. **数据前**：确认画像字段、任务类型和冲突语义；
2. **SFT 前**：确认消息格式、样本配比和数据审计结果；
3. **GRPO 前**：根据 SFT 失败模式确认 Reward 项和权重；
4. **正式评测前**：冻结模型、任务、指标和对照组。

若实施中需要改变本契约中的目标、信息优先级、数据隔离或评测归因，必须先修改契约并说明原因；
普通超参数和样本规模调整不需要重做项目级设计。

## 12. 完成定义

项目只有在以下产物全部具备时才视为完成：

- 一条从数据准备到 SFT、GRPO、评测的可执行命令链；
- 可审计的自采集个性化多轮轨迹；
- 支持画像和 `ask_user` 的 Agent/环境闭环；
- 确定性、带单测的新 Reward；
- 三轨评测及最小消融表；
- 训练曲线、典型成功/失败轨迹和诚实的限制说明；
- README 中清晰区分开源继承部分与个人实现部分。
